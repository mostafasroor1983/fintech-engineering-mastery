## Memory layout
Q: Describe the JVM memory areas a backend engineer should know.
A: Heap (objects; young and old generations or regions, managed by GC), thread stacks (frames and locals, one per platform thread; virtual threads keep stacks on the heap), Metaspace (class metadata, native memory), code cache (JIT-compiled code), and direct/native memory (NIO buffers, Netty, compression libraries). Containers kill the process on total memory, not just heap, so all of these count.

Q: What is an `OutOfMemoryError: Metaspace` and its typical cause?
A: Class metadata exhausted native Metaspace: usually a class-loader leak (redeploying in an app server, dynamic proxies or scripting engines generating classes per request, e.g. compiling a Groovy rule per call). Each class loader that stays reachable keeps all its classes. Fix the leak (cache compiled classes, close loaders), and cap with `-XX:MaxMetaspaceSize` so it fails visibly.

Q: How does object allocation work, and why is short-lived garbage cheap?
A: Threads allocate in thread-local allocation buffers (TLABs) by bumping a pointer: very fast. Most objects die young, and young collections only copy live objects, so the cost is proportional to survivors, not garbage. Long-lived objects that are promoted and then die (caches, session data) are what make old-generation collections expensive.

Q: What is escape analysis and how does it reduce allocation?
A: The JIT proves an object never escapes a method or thread, then applies scalar replacement (keeping its fields in registers or on the stack instead of allocating) and lock elision. Small value objects in hot loops can cost nothing. It's an optimisation, not a guarantee, so measure with JMH and allocation profiling rather than assuming.

Q: How big is a Java object, and why does it matter for in-memory caches?
A: A header (12 bytes with compressed class pointers on 64-bit, 8 with compact object headers in JDK 24+ when enabled), plus fields, aligned to 8 bytes. A `Long` costs about 16 bytes instead of 8, and a `HashMap` entry about 32–48 bytes plus key and value. Caches of millions of boxed entries use several times the expected memory; use primitive collections or off-heap stores for large data.

## Garbage collection
Q: Compare G1, ZGC and Parallel GC. Which would you choose for a payment API?
A: Parallel maximises throughput with longer stop-the-world pauses (batch jobs). G1 (the default) is region-based with a pause-time goal (`MaxGCPauseMillis`, 200 ms default): a good default for services. ZGC does concurrent compaction with sub-millisecond pauses largely independent of heap size, at some CPU and memory overhead, and is generational since JDK 21 (default mode from JDK 23). For a latency-sensitive payment API with a large heap, ZGC; otherwise G1, measured.

Q: What does a GC log tell you, and how do you enable it?
A: `-Xlog:gc*:file=gc.log:time,uptime,level,tags`. It shows pause times and causes, heap before and after, promotion, humongous allocations and concurrent cycle timing. Look for pause times against your SLO, frequency of young GCs (allocation rate), old-generation growth after collections (possible leak) and to-space exhausted or allocation-failure events.

Q: What are humongous objects in G1 and why do they hurt?
A: Objects of at least half a region are allocated directly in contiguous old-generation regions, which wastes space, fragments the heap and can trigger full GCs. Typical sources: huge byte arrays from reading whole files or responses, giant `StringBuilder`s. Stream large payloads, or increase `G1HeapRegionSize` if unavoidable.

Q: Your service's p99 latency spikes every few minutes. How do you tell if GC is the cause?
A: Correlate the spikes with GC pause times from GC logs or JFR (`jdk.GarbageCollection`) and the `jvm.gc.pause` Micrometer metric. If they match, check the allocation rate and old-gen growth. If not, look elsewhere: connection pool waits, safepoints (`-Xlog:safepoint`), CPU throttling in the container (`container_cpu_cfs_throttled_seconds_total`), or downstream latency.

Q: What is a full GC in G1, and what usually triggers it?
A: A stop-the-world collection of the whole heap (multi-threaded since JDK 10, but still a long pause), the fallback when concurrent marking can't keep up, evacuation fails (to-space exhausted), or humongous allocation can't find space. It means the heap is too small for the live set and allocation rate, or concurrent marking starts too late; tune heap size and `InitiatingHeapOccupancyPercent` after finding the root cause.

Q: What is the difference between throughput and latency in GC tuning?
A: Throughput is the share of time not spent in GC; latency is the length of individual pauses. Larger young generations improve throughput but can lengthen pauses; concurrent collectors cut pauses at the cost of CPU. Decide which matters for this service (batch vs API) and tune against measured SLOs, not defaults from blog posts.

Q: Should you call `System.gc()`?
A: No. It requests a full GC (stop-the-world for most collectors) and is usually a sign of a design problem. Libraries sometimes call it (for example to free direct buffers); `-XX:+DisableExplicitGC` or `-XX:+ExplicitGCInvokesConcurrent` contain the damage.

## Memory leaks
Q: How do you find a memory leak in a running Java service?
A: Confirm with metrics: old-gen usage after each GC rising over hours. Take a heap dump (`jcmd <pid> GC.heap_dump`, or `-XX:+HeapDumpOnOutOfMemoryError`) and analyse it in Eclipse MAT: the dominator tree and "leak suspects" show which objects retain the most memory and the GC root path keeping them alive. Compare two dumps taken apart in time to see what grows.

Q: Name common memory leak patterns in Spring services.
A: Unbounded caches (`static Map` with no eviction), listeners or callbacks registered and never removed, `ThreadLocal` values not cleared in pooled threads, per-request class generation (Metaspace), large result sets loaded into memory (`findAll()`), unclosed streams and resources holding buffers, and sessions or in-memory queues growing under load.

Q: Is a heap dump safe to take in production, and what's in it?
A: It pauses the JVM for seconds to minutes depending on heap size, and the file contains all in-memory data: card numbers, tokens, personal data. Take it from an instance removed from the load balancer, store it encrypted with restricted access, and treat it as sensitive data with a deletion policy.

Q: Your container is OOM-killed but the Java heap looks fine. Why?
A: The kernel killed the process for exceeding the container memory limit, which includes non-heap memory: Metaspace, thread stacks, code cache, direct buffers, GC structures and native libraries. Set `-XX:MaxRAMPercentage` around 70–75% so the heap leaves headroom, use Native Memory Tracking (`-XX:NativeMemoryTracking=summary`, `jcmd VM.native_memory`) to find the growth, and cap direct memory.

## JIT, startup and runtime
Q: What is JIT compilation and why does it matter for benchmarks and deployments?
A: The JVM interprets code first, then compiles hot methods (C1, then optimised C2) based on runtime profiles. Fresh instances are slower until warmed up, so latency spikes after deploys and naive benchmarks measure the interpreter. Warm up before taking traffic (readiness after warm-up), and benchmark with JMH, which handles warm-up and dead-code elimination.

Q: What are CDS, AOT cache and GraalVM native image, and when would you use them?
A: Class Data Sharing (and the JDK 24+ AOT cache from Project Leyden) stores pre-parsed and pre-linked classes to cut startup time. GraalVM native image compiles the app ahead of time into a binary: very fast startup and low memory, but a closed-world assumption (reflection needs configuration), longer builds and different peak performance. Use native images for scale-to-zero functions and CLIs; long-running payment services usually stay on the JVM.

Q: Why should you measure with JMH rather than `System.currentTimeMillis()` loops?
A: Naive loops are distorted by JIT warm-up, dead-code elimination (unused results are optimised away), constant folding, on-stack replacement and GC. JMH handles warm-up and measurement iterations, forks JVMs, consumes results through `Blackhole`, and reports error margins. Even then, benchmark realistic data and confirm with production profiling.

Q: What is a safepoint, and how can it cause latency you don't see in GC logs?
A: A point where all application threads stop so the JVM can do work (GC, deoptimisation, biased-lock revocation in old JVMs, thread dumps). Time-to-safepoint can be long if a thread runs a counted loop without a safepoint poll. Enable `-Xlog:safepoint` to see total stopped time versus GC time.

## Containers and configuration
Q: How should you configure JVM memory in Kubernetes?
A: Set container memory request and limit (equal for predictable QoS), then let the JVM size the heap from the limit with `-XX:MaxRAMPercentage=70` to 75 rather than a fixed `-Xmx` that drifts from the limit. Leave room for Metaspace, threads, direct memory and the GC. Make sure the JVM is container-aware (all modern JDKs are) and watch native memory too.

Q: How do CPU limits in containers affect a JVM?
A: The JVM sizes GC and compiler threads and the common pool from the CPU count it sees (from the CPU limit). CFS quota throttling pauses the whole container when the quota is used up within a period, creating latency spikes that look like GC pauses. Many teams set CPU requests but no CPU limit for latency-sensitive services; check `-XX:ActiveProcessorCount` if detection is wrong.

Q: What JVM flags would you always set for a production service?
A: Heap sizing by percentage (`-XX:MaxRAMPercentage`), GC logging to a file with rotation, `-XX:+HeapDumpOnOutOfMemoryError` with a writable path, `-XX:+ExitOnOutOfMemoryError` (crash and restart rather than limp on), JFR continuous recording (`-XX:StartFlightRecording` with a size limit) and an explicit GC choice. Keep the list short and justified.

## Profiling and diagnosis
Q: CPU is at 100% on one instance. How do you find the cause?
A: Find the hot threads: `top -H` and then a thread dump matched by native thread id, or better, async-profiler in CPU mode for 30 seconds to get a flame graph. Typical culprits: a tight loop, regex backtracking, excessive GC (check GC CPU time), serialization of huge objects, or logging. Check whether it's user code or GC threads first.

Q: What is a flame graph and how do you read it?
A: An aggregated view of sampled stack traces: the x-axis is the share of samples (not time order), the y-axis is stack depth, and wide frames are where time is spent. Look for wide plateaus at the top (self time) and unexpected wide subtrees (serialization, reflection, logging). Compare before/after flame graphs to confirm a fix.

Q: Wall-clock vs CPU profiling: when do you use each?
A: CPU profiling shows where threads burn CPU. Wall-clock profiling samples all threads regardless of state, showing where they wait (locks, I/O, pool queues): the right tool when latency is high but CPU is low. async-profiler supports both (`-e cpu`, `-e wall`), plus allocation and lock modes.

Q: What is JDK Flight Recorder, and is it safe in production?
A: A low-overhead (typically around 1%) event recorder built into the JVM: GC, allocations, locks, I/O, exceptions, thread states and custom events. Run it continuously with a bounded buffer and dump on demand (`jcmd <pid> JFR.dump`) after an incident; analyse with JDK Mission Control. It's designed for production.

Q: How do you diagnose high allocation rate, and why does it matter?
A: GC logs or the `jvm.gc.memory.allocated` metric show the rate; async-profiler's allocation mode (`-e alloc`) or JFR allocation samples show which code allocates. High allocation drives frequent young GCs and can increase pause times and CPU. Common fixes: avoid boxing in hot paths, reuse buffers carefully, stream instead of materialising large collections, reduce logging string building.

Q: A thread dump shows 200 threads WAITING in `HikariPool.getConnection`. Diagnosis?
A: Connection pool exhaustion: more concurrent requests need a connection than the pool has. Causes: slow queries holding connections, connections held across remote calls inside a transaction, a leak (connection not returned), or too much concurrency (virtual threads). Check pool metrics (active, pending, usage time), enable `leakDetectionThreshold`, shorten transactions, and add limits.

Q: What are the states in a thread dump, and what do they suggest?
A: RUNNABLE (running or in native I/O, e.g. socket read), BLOCKED (waiting for a monitor: lock contention), WAITING/TIMED_WAITING (parked on a condition, `sleep`, `join`, pool queue). Many BLOCKED on one lock means contention; many RUNNABLE in socket reads means a slow dependency; many WAITING on a pool means exhaustion. Take several dumps to see what persists.

## Performance engineering
Q: How do you approach a performance problem methodically?
A: Define the goal (p99 latency, throughput, cost), measure with production-like load, find the bottleneck with profiling and metrics (use the USE method for resources and RED for services), change one thing, measure again, and stop when the goal is met. Most problems are in queries, remote calls and serialization, not micro-optimisations.

Q: Why do you look at p99 and p999 latency, not averages?
A: Averages hide the tail. With fan-out (a page calling 10 services), the chance that at least one call hits a slow tail is much higher, so tail latency dominates user experience. Watch percentiles from histograms (not averaged percentiles across instances), and check coordinated omission in your load tool.

Q: What is coordinated omission in load testing?
A: When a load generator waits for a slow response before sending the next request, it sends fewer requests during slow periods and under-reports latency. Use open-model load tools with a constant arrival rate (k6 arrival-rate executors, Gatling's open injection, wrk2) that record latency from the intended send time.

Q: How does JSON serialization become a bottleneck, and how do you fix it?
A: Large payloads, reflection-heavy mapping, deep object graphs and repeated `ObjectMapper` creation. Fixes: reuse one configured mapper (it's thread-safe), use records with afterburner-style optimisations or code generation, stream large responses, paginate, and avoid serialising entities with lazy relationships (N+1 plus huge graphs).

Q: How do you reduce latency for a service that calls three downstream services sequentially?
A: Call independent services in parallel (structured concurrency or `CompletableFuture` with a dedicated executor), cache stable data, set timeouts with a total budget, and consider whether some calls can move off the request path (async enrichment via events). Measure the critical path, not the sum.

Q: What is the cost of logging in a high-throughput service?
A: String building, synchronous appenders blocking on disk or network, and massive volume (cost and noise). Use parameterised logging (`log.debug("x {}", y)`), async appenders with bounded queues and a drop policy for low-value logs, structured JSON with sampled debug logs, and never log full payloads with personal data.

Q: What are the main causes of slow startup in Spring Boot apps, and how do you fix them?
A: Classpath scanning, many auto-configurations, eager initialisation of heavy beans, Flyway migrations at start, and JIT warm-up. Fixes: trim dependencies, `spring.main.lazy-initialization` where acceptable, CDS/AOT cache (`-XX:AOTCache` on JDK 25, or Spring's CDS support), Spring AOT processing, and GraalVM native image for extreme cases.

Q: How do you load test a payment service realistically?
A: Production-like data volume and distribution (hot accounts, realistic amounts), realistic mix of operations, open-model arrival rate at expected peak and 2–3× peak, real dependencies or faithful stubs with latency and failure injection, run long enough to see GC and leaks, and measure the right SLIs. Check correctness after the test too: no duplicates, ledger balanced.

Q: What is Little's Law, and how do you use it for capacity planning?
A: L = λ × W: average concurrency equals arrival rate times average time in the system. At 500 requests/s and 200 ms average latency, about 100 requests are in flight, so a pool or connection limit below 100 will queue. Use it to size thread pools, connection pools and semaphores, and to sanity-check load test results.

Q: How does garbage collection interact with virtual threads?
A: Virtual thread stacks live on the heap as stack chunks, so millions of parked virtual threads increase heap usage and GC work (they're scanned as heap objects rather than as roots). Very deep stacks in virtual threads cost memory. It's usually a good trade, but size the heap with your concurrency level in mind.

Q: What is the difference between `-Xmx`, `-Xms` and `MaxRAMPercentage`, and should `Xms` equal `Xmx`?
A: `-Xmx` caps the heap, `-Xms` sets the initial size; `MaxRAMPercentage`/`InitialRAMPercentage` express them relative to container memory. Setting initial equal to max avoids resize pauses and makes memory use predictable in containers (the memory is committed anyway), at the cost of committing memory up front. Common choice for services: equal, with percentage-based sizing.

Q: Why might `String.intern()` or huge string deduplication help or hurt?
A: Interning deduplicates repeated strings (currency codes, status values) but the string table has costs and interning everything adds CPU. G1's string deduplication (`-XX:+UseStringDeduplication`) does it in the background for long-lived strings. For a fixed set of values, use enums or constants instead.

Q: How do you investigate a slow endpoint end-to-end?
A: Start from a distributed trace of a slow request: find the longest spans (database, downstream call, waiting for a connection). Then drill down: `EXPLAIN (ANALYZE, BUFFERS)` for slow queries, profiler for CPU-heavy code, pool metrics for waits. Fix the dominant span and confirm the improvement in the percentile metrics.

Q: What is the N+1 query problem, and how does it show up in a profile?
A: Loading N parent rows then lazily loading each child collection issues N+1 queries. In traces it shows as many tiny identical queries under one request; in profiles as time in the JDBC driver and Hibernate. Fix with a fetch join, `@EntityGraph`, batch fetching or a projection query that returns exactly what the endpoint needs.

Q: When would you consider off-heap memory, and what are the risks?
A: For very large caches or buffers that would otherwise inflate GC work (market data, large lookup tables), via direct `ByteBuffer`s, the Foreign Function & Memory API (final in Java 22) or a library like Chronicle. Risks: manual lifecycle (leaks the GC won't catch), serialization costs, and memory that counts against the container limit but not the heap metrics.

Q: What are soft, weak and phantom references, and should you build caches with them?
A: Weak references are cleared at the next GC once the object is only weakly reachable (`WeakHashMap` keys, canonicalising maps). Soft references are cleared under memory pressure, which makes cache size depend on GC behaviour and can cause sudden GC storms. Phantom references (with `Cleaner`) schedule cleanup after an object dies. Build caches with explicit size and TTL bounds (Caffeine), not soft references.

Q: Why are finalizers deprecated, and what replaces them?
A: `finalize()` runs at an unpredictable time (or never), slows GC, can resurrect objects and has security problems; it's deprecated for removal. Release resources explicitly with try-with-resources (`AutoCloseable`), and use `java.lang.ref.Cleaner` only as a safety net for native resources.

Q: Why does upgrading the JDK (for example 17 to 21 or 25) often improve performance with no code change, and what should you test?
A: Newer JDKs bring better GC (generational ZGC, G1 improvements), JIT optimisations, faster startup features and library improvements. Test: GC behaviour and pause times under load, removed or changed flags (the JVM refuses to start with obsolete options), reflective access to JDK internals (strong encapsulation), and library compatibility. Roll out with canaries and compare metrics.

Q: How do you decide between scaling up (bigger instances) and scaling out (more instances) for a JVM service?
A: Scale out for stateless services when load is spread evenly and you want resilience; scale up when per-instance overhead (heap for caches, warm-up, connections per instance to the database) dominates or the workload doesn't partition. Watch the database: every new instance adds connections, so pool size × instances must stay within the database's limits (or use PgBouncer).

Q: What does "allocation rate" have to do with cloud cost?
A: Allocation drives GC CPU. A service allocating several GB/s spends a meaningful share of its CPU in GC, which means more or larger instances for the same traffic. Reducing allocation in hot paths (boxing, temporary collections, logging strings) lowers both latency and the bill; measure GC CPU share before and after.
