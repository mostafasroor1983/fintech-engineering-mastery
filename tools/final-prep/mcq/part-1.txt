Q: A customer double-clicks "Pay". Both requests reach two different instances of your payment API at the same millisecond with the same Idempotency-Key. What guarantees only one payment is created?
- An in-memory `synchronized` block around the create method
- Checking whether the key exists before inserting the payment
* A unique constraint on (client_id, idempotency_key), inserted in the same transaction as the payment
- A Redis lock with a 5-second TTL around the request
E: Only the database can arbitrate between instances atomically. An in-memory lock covers one instance, check-then-insert races, and a TTL lock can expire while the holder is paused.

Q: The call to your PSP times out after 10 seconds. What should the payment's status become?
- FAILED, so the customer can retry immediately
* UNKNOWN (pending), resolved later by querying the PSP or by reconciliation
- SUCCEEDED, because timeouts usually mean slow success
- CANCELLED, and a reversal is sent to the PSP
E: A timeout means you stopped waiting, not that the charge failed. Marking it FAILED invites a second payment; you must resolve the real outcome.

Q: Your service splits £10.00 equally between three merchants using `amount.divide(3, HALF_UP)` on each share. What is the result?
- £10.00 is split exactly
- The total is £10.01
* The total is £9.99: one penny is lost
- An `ArithmeticException` is thrown
E: 3.33 × 3 = 9.99. Use largest-remainder allocation so shares sum exactly to the original amount.

Q: A colleague writes `new BigDecimal(0.1)` to represent ten pence. What is the problem?

* It holds the binary approximation 0.1000000000000000055…, not exactly 0.1
- It's only a problem on 32-bit JVMs
E: The double literal is already imprecise. Use `new BigDecimal("0.10")` or minor units in a `long`.

Q: Two concurrent transfers run A→B and B→A, each locking its source account first, then the destination. What happens under load?
- Both always succeed because locks are reentrant
* They can deadlock, each waiting for the lock the other holds
- One transfer is silently lost
- The JVM detects the cycle and retries one automatically
E: Opposite lock orders create a cycle. Lock accounts in a global order (by id) to make deadlock impossible.

Q: A balance check reads the balance in Java, compares it, then issues `UPDATE accounts SET balance = :newBalance`. What's the risk under READ COMMITTED?
* Lost updates and overdrafts when two requests interleave
- No risk: READ COMMITTED prevents lost updates
- Only a risk on MySQL, not PostgreSQL
- Deadlocks, but never wrong balances
E: Read-modify-write in application code races. Use a conditional atomic update (`WHERE balance >= :x`), `SELECT … FOR UPDATE`, or `@Version`.

Q: You enable virtual threads in a Spring Boot service with a HikariCP pool of 10 connections. Under peak load, requests start timing out. Most likely cause?

- The JIT can't compile code running on virtual threads
E: Virtual threads raise concurrency; the downstream limit (the connection pool) becomes the bottleneck. Size limits explicitly and add timeouts.

Q: A method annotated `@Transactional` is called from another method in the same class. The inner method throws a RuntimeException. What happens?

E: Self-invocation doesn't go through the Spring proxy, so `@Transactional` on the inner method has no effect.

Q: A service method catches `SQLException`-derived checked exceptions and rethrows them as a checked `PaymentException`. The transaction commits partial work. Why?

Q: Kafka consumers in your group keep rebalancing every few minutes during peak load. Processing a poll of 500 records takes up to 6 minutes. What's the most likely cause?

Q: You need all events for one account processed in order across a 12-partition Kafka topic. What do you do?

- Enable `enable.idempotence=false` to avoid reordering
E: Kafka orders within a partition; keying by account sends all its events to one partition while keeping parallelism across accounts.

Q: Your consumer writes to PostgreSQL and the producer uses Kafka transactions with `read_committed` consumers. A consumer crashes after the database commit but before the offset commit. What happens on restart?

- The database transaction is rolled back automatically

- The record is skipped
E: Kafka's exactly-once covers Kafka-to-Kafka. Database effects need idempotent consumers (a processed-events table in the same transaction).

Q: A service writes an order to the database and then publishes an event to Kafka. Sometimes events are missing. Best fix?
- Publish to Kafka first, then write to the database
- Retry the Kafka publish forever in the request thread
* Use a transactional outbox: write the event row in the same DB transaction and relay it
- Use XA transactions between PostgreSQL and Kafka
E: This is the dual-write problem. The outbox makes the event part of the commit; a relay publishes it at least once.

Q: A colleague proposes a Redis lock (Redlock across 5 nodes) to prevent double spending on wallet balances. What is the main flaw?

* A paused client can outlive its lock's TTL and still write; correctness needs fencing or a database constraint
- Five nodes are too few for Redlock
- Redlock only works with Redis Cluster
E: Leases can expire while the holder is paused (GC, network). Enforce the invariant at the write with a conditional update or constraint.

Q: During a network partition, your ledger service must never show two different balances for the same account. Which CAP choice does that imply?

Q: A Raft cluster has 5 nodes. How many can fail while the cluster still commits writes?

Q: You read a payment from a read replica right after creating it on the primary, and get "not found". What's happening?

- A serialization failure

E: Asynchronous replicas lag. Read your own writes from the primary or wait for the replica to reach the commit position.

Q: Which isolation level in PostgreSQL prevents write skew (two transactions each reading a shared limit and inserting rows that together break it)?

- REPEATABLE READ
* SERIALIZABLE
- READ UNCOMMITTED
E: Snapshot isolation (REPEATABLE READ) allows write skew; PostgreSQL's SERIALIZABLE (SSI) detects it. Alternatively lock a shared row.
